# TypeScript-библиотека Gothic Lock Solver

Статус: **черновик для согласования, реализация не начата**.
Дата: 2026-09-07. Текущая задача ограничена нашим репозиторием.

## Цель и границы

Превратить проверенный решатель в читаемую, типизированную и воспроизводимо
публикуемую библиотеку. Потребитель подключает один готовый файл и получает
последовательность открытия замка по состоянию и связям.

Референс сохраняется в `feat/matrix-astar-benchmarks`, commit
`3cbbeedbb409a2d8ffa5b00c778cfcb0b07c0ec6`. Код бенчмарка выполнен на доступном
commit `6b1cfbc13bcec68f609d45d5dc97504dd84f1760`; результаты находятся в
`docs/benchmarks/run-20260907T070258001Z-f78dff13`.

Новая ветка `feat/typescript-core-library` начинается от референса. Её PR сначала
направляется в референсную ветку, чтобы показывать только преобразование библиотеки.
Слияние в `main`, активация публикации и сторонние PR в этот этап не входят.
Workflow публикации будет подготовлен и проверен; боевой выпуск запускается после
будущего одобренного слияния в `main`. Собственный сайт и UI не создаются.

## Публичный контракт — уточнённое предложение

```ts
type Position = 1 | 2 | 3 | 4 | 5 | 6 | 7;
type Link = -1 | 0 | 1;
type Delta = -6 | -5 | -4 | -3 | -2 | -1 | 1 | 2 | 3 | 4 | 5 | 6;
type State = readonly [Position, Position, ...Position[]];
type Command = readonly [index: number, delta: Delta];

function solveLock(
  state: State,
  links: readonly (readonly Link[])[],
): readonly Command[] | null;
```

Ровно два аргумента. N выводится из `state.length`; отдельные N, цель, алгоритм,
бюджеты, callbacks и настройки в публичный вызов не добавляются. Внешнее API
не возвращает телеметрию или оболочку с копиями входа. Для литерального tuple N
типизация дополнительно проверяет размер links, выводя его только из state.
Для данных динамической длины обязательна runtime-проверка квадратности.

**Подтверждённое представление состояния:** tuple позиций `[1,7,4,…]`, по одному
значению на пластину. Каждая строка визуального поля N×7 описывается одним числом.
Пользователь подтвердил этот формат и предложил компактную команду из двух чисел.

- Модель допускает N≥2; позиции — целые 1…7, цель — все 4.
- `links` имеет размер N×N, значения −1/0/1, диагональ 0.
- `links[source][target]` задаёт прямое направленное влияние без каскада.
- `index` в командах — целый индекс 0…N−1, совпадающий с индексом управляемой
  позиции state и строкой links. В модели замка это выбранная пластина;
  для подписи «пластина №1» UI прибавляет единицу.
- Значения Position сохраняют игровую нумерацию 1…7, цель 4. Нумерация
  элементов массива и нумерация отверстий — разные части контракта.
- `delta > 0` увеличивает выбранную числовую позицию; `delta < 0` уменьшает.
  В публичном математическом контракте нет физических направлений left/right.
  `abs(delta)` — число делений, максимум 6. Нулевая delta не возвращается:
  отсутствие действий уже выражается пустым массивом.
- Каждая команда и её промежуточные деления допустимы; входы не изменяются.
- `[]` означает уже открытый замок; `null` — доказанную недостижимость цели.
- Невалидный ввод и исчерпание ресурсов дают различимые документированные ошибки.
  Ресурсный предел никогда не преобразуется в `null`.
- Функция синхронна, детерминирована и безопасна для повторных независимых вызовов.
  Для тяжёлых входов потребитель может вызвать её в Worker.

### Математические координаты — обязательный инвариант

По последнему уточнению пользователя ядро работает с изменением числовой позиции
штифта. Перевод в физическое движение пластины принадлежит интегратору.
Команда `[i, delta]` задаёт:

```text
x'_j = x_j + delta × (j === i ? 1 : links[i][j])
x'   = x + delta × (I + linksᵀ) × e_i
```

Границы проверяются для всех затронутых пластин; при нарушении движение целиком
недопустимо. Связи не замыкаются транзитивно. Разворот строк в UI не изменяет
знак команды или индексы в данных.

Контрольный асимметричный пример:

```ts
solveLock([6, 2], [[0, -1], [0, 0]])
// [[0, -2]]: первая позиция 6→4; реверсивная связь меняет вторую 2→4.
```

Точное преобразование старого результата для сравнения:
`index = old.plate - 1`,
`delta = old.direction === 'left' ? old.steps : -old.steps`.
Для исходного единичного хода UnlockMyLoot: `delta = d`.
Его UI при показе физического движения пластины использует обратный знак.
Этот обратный знак применяется только в клиентском адаптере, не к state,
links или командам ядра. Названия left/right старой реализации не переносятся
в новый публичный контракт.

Выбор координат не меняет критерий оптимизации. Одно `[index, delta]` стоит
одно действие A независимо от `abs(delta)`; C равно сумме `abs(delta)`,
U — количеству разных index. Интегратор может менять подписи и направление
отображения, но не переставлять команды произвольно: порядок защищает границы.
Минимум действий находит ядро. Выбор другой целевой функции был бы отдельным
изменением алгоритмического контракта, а не настройкой отображения.

Проверки закрепляют пример выше, отсутствие обратной связи, атомарное отклонение
выхода любой связанной пластины за 1…7, отсутствие каскада, пустой результат,
доказанную недостижимость и отсутствие нулевых команд. Это намеренное изменение
публичного контракта; README и release notes должны объяснять миграцию.

Пределы конкретного поиска отделены от механики. Текущая безопасная числовая
кодировка допускает N≤18; расширение кодировки сверх этого не является задачей
миграции. Нет специального ограничения N≤8 в модели библиотеки.

## Алгоритм и структура

Сохраняем точную рациональную матричную подготовку, достаточный сертификат пути,
A* с согласованной нижней оценкой и точный BFS для вырожденной матрицы.
Основная гарантия — минимум количества действий A. Разные выбранные пластины U
и единичные сдвиги C измеряются отдельно; общий минимум U/C среди равных по A
путей не обещается.

Применяем SOLID, KISS, YAGNI и DRY к текущей задаче:

- один публичный facade и одна реализация механики;
- объект модели замка отвечает за проверенный неизменяемый ввод и эффекты;
- стратегии A* и BFS имеют небольшой внутренний общий контракт;
- приоритетная очередь и бюджет поиска инкапсулируют своё состояние;
- точная арифметика и преобразования остаются чистыми функциями там, где класс
  не даёт дополнительной ответственности;
- композиция без иерархий ради ООП, DI-контейнеров, реестров и плагинной системы;
- CLI остаётся отдельным адаптером и не входит в распространяемое ядро;
- диагностические инструменты бенчмарка не расширяют публичные два аргумента.

### Строгость, которая проверяется инструментами

Исходники — TypeScript с `strict: true`, `noUncheckedIndexedAccess`,
`exactOptionalPropertyTypes`, `noImplicitOverride`, `noImplicitReturns`,
`noFallthroughCasesInSwitch`, `noPropertyAccessFromIndexSignature`,
`noUnusedLocals`, `noUnusedParameters`, `noUncheckedSideEffectImports`,
`verbatimModuleSyntax` и `isolatedModules`. Unreachable code и unused labels
запрещены; `skipLibCheck: false`. Применимость флагов проверяется выбранным
актуальным компилятором, без отключения диагностики ради сборки.

Нет `any`, `@ts-ignore`, необоснованных type assertions и non-null assertions.
`@ts-expect-error` допустим только в отрицательных тестах типового контракта:
тест должен доказывать, что недопустимый вызов отвергается компилятором.
На runtime-границе проверяются целочисленность, диапазоны, длины и отсутствие
дыр в массивах. `readonly` в типах не подменяет эти проверки или проверку
отсутствия мутации входов. Ошибки линтера и обязательных проверок блокируют CI.

Матричная алгебра точная, без epsilon и приблизительных сравнений ранга.
Поиск не подменяется эвристическим приблизительным ответом при исчерпании
ресурсов. Математические гарантии обосновываются отдельно от тестовых примеров.
Runtime-зависимостей нет; инструменты разработки являются devDependencies.

### GitHub Actions: только официальные актуальные подключения

По явному требованию пользователя каждый внешний `uses:` ссылается на Action,
поддерживаемый автором соответствующего сервиса или инструмента. Владение
репозиторием и статус поддержки проверяются по официальным источникам.
Marketplace badge сам по себе не заменяет эту проверку.

- GitHub: `actions/checkout`, `actions/setup-node`, `actions/upload-artifact`
  и `actions/download-artifact` там, где этап действительно использует artifacts.
- pnpm: официальный `pnpm/action-setup` для установки менеджера пакетов.
- npm-публикация: официальный npm CLI с OIDC; отдельная Action-обёртка не нужна.
- GitHub Releases: официальный GitHub CLI `gh` для draft, assets и финализации.
- Playwright/Vitest запускаются официальными CLI из закреплённых зависимостей.

На момент добавления/обновления выбирается последний стабильный релиз каждого
Action. В workflow сохраняется его полный commit SHA из исходного репозитория,
рядом комментарий с точным release tag. Таким образом, повторный запуск использует
ту же реализацию Action. Плавающие main/master/latest и prerelease не используются.
Если latest требует обновления среды, обновляется поддерживаемая среда;

## Четыре распространяемых файла

| Файл | Подключение |
|---|---|
| `gothic-lock-solver.mjs` | Читаемый ESM: браузер или Node.js import |
| `gothic-lock-solver.min.mjs` | Минифицированный ESM |
| `gothic-lock-solver.js` | Читаемый classic script, глобальный `GothicLockSolver.solveLock` |
| `gothic-lock-solver.min.js` | Минифицированный classic script |

Каждый файл самодостаточен: без внешних imports, дополнительных chunks, обращения
к сети, Node API и UI. Сборка использует один TypeScript entry point, форматы
ESM и IIFE. Минификация не меняет контракт, ошибки и найденный результат.
Текущий ручной ESM-assembler заменяется стандартной сборкой Vite.

Проверяется настоящая минификация обоих `.min` файлов: стандартная настройка
Vite library mode сама по себе может сохранять пробелы в ESM. Если нужен отдельный
финальный проход минификатора, он входит в нашу сборку и проверяется на выходе.

Декларации типов для ESM-путей, описание глобального API, лицензия и manifest
с версией, commit SHA и хэшами сопровождают выпуск. Это вспомогательные файлы;
для исполнения потребитель выбирает ровно один из четырёх runtime-файлов.

## Проверки реального использования

Vitest projects разделяют Node и настоящий браузер через Playwright. `jsdom`
или изолированный Node VM не считаются подтверждением браузерной совместимости.
Начальная браузерная матрица: Chromium, Firefox, WebKit.

Agent Browser рассмотрен отдельно: это CLI управления настоящим браузером для
агента, а не математический тестовый runner и не симулятор DOM. Для обязательной
матрицы CI остаётся документированный провайдер Vitest + Playwright. Agent Browser
может использоваться при дополнительной диагностике реального подключения;
вторая обязательная параллельная система тестов не создаётся.

1. Общий каталог всех 45 входов проверяется в Node и Browser Mode. Каждый путь
   независимо воспроизводится по одному делению и сверяется с точным минимумом A.
2. Малые модели и контрпримеры защищают границы, матричные ложноположительные
   выводы, вырожденность, недостижимость и повторный выбор пластины.
3. Проверяются именно собранные файлы: оба ESM в Node, все четыре варианта
   в браузерах. Для каждого проверяются 45 входов и одинаковый публичный контракт.
4. E2E загружает реальные неизменённые байты dist через HTTP, classic script
   и `script type=module`, а не повторно преобразованный dev-server исходник.
   Проверяются отсутствие дополнительных runtime-загрузок и работа Worker.
5. Отдельный небольшой сценарий проверяет classic script через `file://`;
   локальный ESM через `file://` не обещается.
6. Неподдерживаемая среда или невозможность запустить браузер явно отражаются
   в результате. Пропущенная обязательная среда не даёт статуса полной готовности.

Покрытие публикуется как диагностический отчёт. Число тестов или процент покрытия
не подменяют независимую проверку механики и производственного импорта.

## Бенчмарк и snapshot

Сохраняем текущие 45 fixtures, происхождение данных, точный baseline и сторонний
решатель на закреплённом commit. Его код читается из отдельного checkout и
проверяется хэшами; AGPL-исходник не включается в наш Apache-репозиторий.

На каждом PR сравниваются candidate и base в одной среде, с прогревом,
чередованием порядка и повторными измерениями. Исторический snapshot остаётся
доказательством прошлых измерений, но не заменяет свежее парное сравнение.
Статистики разных браузеров, Node и разных машин не смешиваются.

Для каждого замка и реализации отчёт содержит A/U/C, переключения, отдельные
замеры времени, median/p95, параметры выборки, версию среды и хэши артефактов.
Также сохраняются размер bundle и измерения памяти с точным названием метрики.

Память Node измеряется отдельным запуском в изолированном процессе: peak RSS
включает runtime и не выдаётся за точное число байтов, выделенных алгоритмом.
Для браузеров портативного точного peak-heap измерения не обещаем: значение
отмечается как недоступное либо приводится отдельно с указанием API и ограничений.
Замер памяти отделён от замера скорости, чтобы инструментация не искажала таймер.

**Правила сравнения:**

- Неверный путь, потеря решаемости, рост A относительно установленного минимума,
  несоответствие контракту или артефакту блокируют CI.
- A/U/C сверяются по каждому замку. При равном A ухудшение U/C требует явного
  обоснования и отдельного принятого изменения snapshot. Миграция в TypeScript
  сама по себе не является таким обоснованием.
- Одиночное отклонение времени/RSS на общей CI-машине не считается доказанной
  регрессией. Отчёт помечает сигнал, проверяет шум и выполняет ограниченный повтор.
- Допуски времени и памяти калибруются на сравнении неизменённой версии с собой
  до включения performance verdict. Они не выбираются ради зелёного результата.
- Детерминированные ресурсные лимиты — строгая проверка. Измеряемые время/RSS —
  отдельный performance verdict с оценкой достоверности, видимый в PR.
- Performance verdict различает `passed`, `regression` и `inconclusive`.
  Недостаточная достоверность не превращается в заявление «регрессии нет»;
  результаты и причина неопределённости сохраняются. Готовность выпуска требует
  принятого результата сравнения, а не только зелёных unit tests.
- Snapshot не перезаписывается автоматически тестами. Его обновление — отдельная
  команда и проверяемый diff с источником, причиной и результатами сравнения.
- Для сравнения используется baseline целевой ветки PR, чтобы candidate не мог
  скрыть ухудшение простым изменением собственного ожидаемого файла.

## CI, npm, GitHub Releases и доставка в браузер

PR запускает lint, typecheck, unit/integration, сборку, тесты dist/E2E и сравнение
бенчмарка. JSON/Markdown, покрытие и четыре файла доступны как CI artifacts.
Документируется одна команда локальной полной проверки и отдельные команды этапов.
PR не публикует боевой `latest` и не получает права деплоя.

**Последнее требование пользователя: публичный npmjs.org, затем GitHub Release.**
Публичный пакет в npmjs.org предназначен для установки и скачивания tarball.
GitHub хранит исходники, CI и релизы с готовыми файлами и доказательным отчётом.
Сторонний CDN, GitHub Packages, Pages и отдельная ветка `distribution` исключены.
Исходная идея прямого `<script src>` на файл из npmjs.org технически не обеспечивается:
официальный registry отдаёт metadata и архив пакета, а не публичный endpoint
распакованного JavaScript. В этом варианте браузерный интегратор размещает один
выбранный файл на своём существующем сайте. Это следствие выбранной доставки,
которое должно быть явно согласовано; реестр не объявляется браузерным CDN.

После будущего слияния в `main` workflow проверяет точный merge commit. Для выпуска
используется одна согласованная SemVer-версия в package.json, npm и GitHub tag.
Имя npm-пакета и права на его scope проверяются до первой публикации;
совпадение GitHub username с npm username не предполагается.

Последовательность выпуска:

1. Пройти обязательные проверки и benchmark gates, собрать четыре runtime-файла
   один раз; упаковать готовый dist с декларациями, package.json, README и лицензией.
   Установка готового пакета не запускает сборку. Пакет не включает каталог
   тестовых замков, внешнее сравниваемое решение и подробные benchmark runs.
2. Установить подготовленный tarball в чистый тестовый проект и проверить публичный
   импорт, типы и четыре формата. Записать контрольные суммы. Сборка при публикации
   повторно не запускается; в npm и Release передаются те же проверенные байты.
3. Опубликовать проверенный tarball как public package в npmjs.org. Планируем
   GitHub Actions trusted publishing через OIDC на GitHub-hosted runner,
   с provenance для публичного пакета из публичного репозитория. Настройка
   npm trusted publisher должна разрешать прямой publish для выбранного workflow.
   Зависимости, сборка и тесты остаются на pnpm; шаг OIDC-публикации использует
   актуальный npm CLI по официальному контракту npm trusted publishing.
   Владение пакетом и первоначальная настройка аккаунта выполняются перед
   первым выпуском, не считаются уже выполненными и не требуют передачи токена в чат.
4. Скачать опубликованный tarball по точной версии, проверить integrity и
   совпадение четырёх файлов с проверенной сборкой. Проверить установку и импорт
   опубликованного пакета в чистом проекте без npm-авторизации.
5. После успешной npm-публикации создать GitHub draft release. Приложить четыре
   runtime-файла из того же tarball, декларации, контрольные суммы и
   `benchmark-evidence.json`. Проверить комплектность и опубликовать Release.
   В release notes — ссылка на точную npm-версию, source SHA и отчёт о сравнении
   с предыдущим стабильным выпуском, включая явный verdict о регрессии/дрейфе.

Публикация npm и GitHub не является общей атомарной транзакцией. Если после
публикации npm проверка пакета или завершение GitHub Release не удались, workflow
сохраняет явный статус частичного выпуска и допускает продолжение с проверкой
идентичности существующего пакета. Он не перепубликует ту же npm-версию и не
удаляет её автоматически. Изменение байтов требует новой версии; временный сбой
доставки допускает ограниченный повтор проверки. До завершения всех этапов выпуск
не объявляется полностью готовым.

Стабильный выпуск связан со слиянием в main, использует стабильную SemVer-версию
и npm dist-tag `latest`. Обычные PR/ветки сохраняют проверенные CI artifacts.
Опциональная канарейка — отдельный ручной запуск для выбранной ветки владельца,
уникальная prerelease-версия с SHA/номером запуска и отдельный npm tag `canary`.
Канарейка не изменяет `latest`, предыдущий стабильный benchmark baseline или
GitHub latest release; если для неё создаётся GitHub Release, он помечается
prerelease. Публичная публикация не запускается автоматически для каждого PR.

Пятый evidence-файл не является зависимостью ядра и не загружается потребителем
при solveLock. У него версионированная JSON-схема: версия выпуска/source SHA,
SHA предыдущего сравниваемого выпуска, fixture/source hashes, версии сред,
параметры измерения, итоги A/U/C и времени/памяти, дельты, quality/performance
verdict и ссылки/хэши подробного отчёта. Для первого выпуска сравнение с нашим
закреплённым референсом явно называется reference baseline, а не предыдущим релизом.
Сторонний pinned baseline в evidence обозначается отдельно.

Файл evidence нужен даже при наличии сводки в release notes: JSON можно проверять
автоматически, а текст описания релиза может редактироваться. Если в репозитории
включены immutable releases, весь набор assets прикладывается до публикации.
Неизменяемость не объявляется настроенной без проверки фактической настройки.

Потребитель выбирает один из двух способов:

1. Установить публичный пакет из npmjs.org через pnpm/npm и импортировать solveLock
   по имени пакета. Публичная установка не требует npm-токена. TypeScript получает
   декларации; пакет имеет явный ESM export. Classic IIFE не выдаётся за CommonJS.
2. Скачать выбранный файл из GitHub Release и разместить рядом с HTML/проектом.
   Также можно скопировать его из установленного npm-пакета. Для сайта достаточно
   добавить один готовый файл в vendor и вызвать API; сборка сайта не требуется.
   Node.js импортирует локальный `.mjs`; поддержка прямого HTTPS-import стандартным
   Node loader не входит в контракт. Release asset URL документируется как ссылка
   скачивания. Скрипт на сайте подключается по URL, который обслуживает сам сайт.

Пример classic-подключения уже скачанного файла:

```html
<script src="./vendor/gothic-lock-solver.min.js"></script>
<script>
  const commands = GothicLockSolver.solveLock([6, 2], [[0, -1], [0, 0]]);
</script>
```

Второй вариант использует локальный `.mjs` в `script type="module"` через import.
Все четыре формата проверяются на статическом HTTP-сервере в реальных браузерах;
это проверка файлов потребителя, а не обещание удалённого CDN. Обновление интеграции
означает явную замену версии/файла, откат — возврат к прежней проверенной сборке.

Файл evidence остаётся отдельным Release asset и не входит в runtime-загрузку.
Манифест контрольных сумм связывает npm-версию и source SHA с байтами runtime-файлов.
Release notes содержат ссылку на npm-версию, команду установки, ссылки скачивания
и примеры подключения локального файла.

## Документация и приёмка

README содержит назначение, алгоритмические гарантии, оба входа и все исходы,
координатные конвенции, четыре способа подключения, Worker, поддержанные среды,
команды проверки, чтение performance verdict, изменение snapshot и выпуск.
AGENTS.md описывает реальные модули, инварианты, команды и границы изменений.
Для работы с публичным проектом доступ к частной wiki не требуется.

Готовность подтверждается проходящим CI нового PR, проверкой всех 45 входов,
принятыми performance-результатами, тестами всех публикуемых форматов и понятным
планом первого выпуска. До согласованного merge стабильная публикация npm/Release
не выполняется; настройка канареек также не считается уже выполненной публикацией.
